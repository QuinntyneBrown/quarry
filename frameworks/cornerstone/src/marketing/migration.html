Migration

Liturgy  ·  Word Up

You do not have to stop shipping to move.

One optional stylesheet keeps your existing class vocabulary rendering while templates move to the Angular API a screen at a time. A half-migrated application still looks finished to the people using it.

See the audited mapping Browse the catalog

Setup

Two lines, in this order.

The theme comes first, the bridge second. The bridge is isolated from the default theme, so an application that never names it downloads none of it.

  1. 01

    Add the package

    The schematic writes the theme entry for you. Adding it by hand works too. 

    $ ng add @quinntyne/cornerstone

  2. 02

    Opt into the bridge

    Order matters: compat.scss after theme.scss, both before your own stylesheet. 

    "styles": [
  "@quinntyne/cornerstone/styles/theme.scss",
  "@quinntyne/cornerstone/styles/compat.scss",
  "src/styles.scss"
]

  3. 03

    Convert a screen

    Swap the legacy markup for the Angular API. This is the step that buys you the keyboard behavior and the ARIA relationships — the bridge alone does not. 

    <!-- before -->
<button class="wu-btn wu-btn--primary">Save</button>

<!-- after -->
<button csButton variant="primary">Save</button>

Scope

What the bridge does, and what it does not.

Does

Reproduces presentation

Word Up's complete wu-* vocabulary and Liturgy's generic product primitives keep rendering the way they do today, painted from Cornerstone tokens.

Does

Stays out of the way

It is a separate export. Applications that do not name it get no extra CSS, so the bridge costs nothing to the projects that never needed it.

Does not

Add behavior

Keyboard interaction, focus management, ARIA relationships, typed outputs, and forms integration arrive only when the template moves to the Angular API.

Does not

Stay forever

It is scaffolding with removal criteria written down in advance, not a permanent second way to build a screen.

Every legacy family has a named successor.

Removal

The bridge comes down when all five hold.

Writing the exit condition down before the work starts is what keeps a compatibility layer from becoming permanent.

  • No legacy selector remains in either application's templates.
  • The component catalog records no open gap.
  • Migrated screens have visual, accessibility, responsive, unit, and end-to-end parity with what they replaced.
  • Nothing references Liturgy's unprefixed legacy token block.
  • The deprecation window announced in the support matrix has closed.

The initial 0.x package carries no breaking migration, and its migration collection is deliberately empty until the first breaking release. When that release arrives, anything an ng update cannot rewrite is reported with the affected file and its manual replacement.

Start with one screen.

Pick the screen you dislike maintaining most. That is usually the one carrying the accessibility debt.
