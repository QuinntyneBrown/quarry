# L2 - Detailed Requirements

Every L2 below traces to exactly one L1 in [`L1.md`](L1.md). Acceptance criteria are written in
Given/When/Then form so each one converts directly into an acceptance test.

**Acceptance test traceability convention.** Every acceptance test file must carry a trace header:

```typescript
// Acceptance Test
// Traces to: L2-055, L2-026
// Description: Checkbox indeterminate state and keyboard operation
```

The trace comment is mandatory. Coverage is verified by scanning test sources for these headers
(see L2-157).

**Shared vocabulary.**

| Term                    | Meaning                                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------------------- |
| Public API              | Any symbol exported from `@quinntyne/cornerstone` or a documented secondary entry point.                       |
| Value-bearing           | A component or directive that owns a form value and therefore implements `ControlValueAccessor`.        |
| Composite               | A catalog section 6-8 component that receives a view model input and emits intent outputs only.         |
| Viewport XS/SM/MD/LG/XL | <576px / >=576px / >=768px / >=992px / >=1200px respectively (see L2-030).                              |
| Intent output           | An `output()` that reports user intention without performing navigation, persistence, or authorization. |

## L2-001: Publishable library package identity

**Traces to:** L1-001

The library must build to a publishable Angular Package Format artifact named `@quinntyne/cornerstone`.
`src/cornerstone/package.json` must declare `name: "@quinntyne/cornerstone"`, a `license`, a
`repository`, a `homepage`, a `bugs` URL, `keywords`, and `sideEffects: false`.

**Acceptance Criteria:**

1. Given a clean checkout, when `npm run build:library` runs, then `dist/cornerstone/package.json` exists with `"name": "@quinntyne/cornerstone"`.
2. Given the built artifact, when its `package.json` is inspected, then `license`, `repository`, `homepage`, `bugs`, `keywords`, and `sideEffects` fields are all present and non-empty.
3. Given the built artifact, when `npm pack --dry-run` runs against it, then the tarball contains `fesm2022` bundles, `.d.ts` declaration files, and no `.ts` source or `.spec` files.
4. Given the built artifact, when it is installed into a fresh Angular application, then importing any public symbol compiles with no additional build configuration beyond installing peer dependencies.

## L2-002: Peer dependency and version contract

**Traces to:** L1-001

The package must declare `@angular/core`, `@angular/common`, `@angular/cdk`, `@angular/forms`, and
`@angular/router` as peer dependencies with permissive ranges, must declare `tslib` as its only
runtime dependency, and must not bundle any Angular package into its output.

**Acceptance Criteria:**

1. Given the built `package.json`, when dependencies are inspected, then `dependencies` contains only `tslib`.
2. Given the built `package.json`, when peer dependencies are inspected, then `@angular/core`, `@angular/common`, `@angular/cdk`, `@angular/forms`, and `@angular/router` are listed with ranges that admit the current major Angular release.
3. Given the built FESM bundles, when their imports are scanned, then no Angular framework code is inlined and all Angular references remain external imports.
4. Given an application that installs the package without `@angular/cdk`, when `npm install` runs, then npm reports an unmet peer dependency naming `@angular/cdk`.

## L2-003: Style and secondary entry point exports

**Traces to:** L1-001

The package must export its theme stylesheet, compatibility stylesheet, and token stylesheet through
declared `exports` subpaths consumable both by the Sass compiler and by plain CSS pipelines, and
these subpaths must resolve from a published tarball, not only from the workspace.

**Acceptance Criteria:**

1. Given an installed package, when a consumer writes `@use '@quinntyne/cornerstone/styles/theme' as *;`, then Sass resolves the file and compiles without error.
2. Given an installed package, when a consumer adds `@quinntyne/cornerstone/styles/theme.scss` to the `styles` array of `angular.json`, then the application builds and the FaithTech tokens are present on `:root`.
3. Given an installed package, when a consumer imports an undeclared subpath, then Node module resolution fails with `ERR_PACKAGE_PATH_NOT_EXPORTED`.
4. Given the published tarball, when its file list is inspected, then every subpath declared in `exports` resolves to a file included in the tarball.

## L2-004: Type declarations and source maps

**Traces to:** L1-001

The published package must ship complete, strict-mode-clean TypeScript declarations and source maps
for every public symbol.

**Acceptance Criteria:**

1. Given a consumer project with `strict: true`, when it imports every public symbol, then `tsc --noEmit` reports zero errors.
2. Given the built artifact, when declaration files are inspected, then no public symbol has an inferred `any` type in its declared inputs, outputs, or return values.
3. Given the built artifact, when FESM bundles are inspected, then a `.js.map` exists for each bundle and resolves to readable original sources.
4. Given a public component, when a consumer passes a value of the wrong type to a signal input, then compilation fails with a type error rather than a runtime error.

## L2-005: FaithTech token surface

**Traces to:** L1-002

The theme stylesheet must define the complete FaithTech token set as CSS custom properties under the
`--cs-` prefix, covering color (ink scale, paper, sand scale, lime, sky, teal, tomato, green, amber,
yellow, and semantic success/warning/error/info with soft variants), typography families and scale,
spacing scale, radius scale, shadow scale, motion duration and easing, focus color, and container
bounds. Every token must be documented.

**Acceptance Criteria:**

1. Given the theme stylesheet applied to a document, when computed styles on `:root` are read, then every token documented in the theming guide resolves to a non-empty value.
2. Given the theming guide, when its token table is compared to the tokens declared in the stylesheet, then the two sets are identical with no undocumented and no missing token.
3. Given any component in the library, when its compiled styles are inspected, then every color, spacing, radius, shadow, duration, and font-family declaration references a `--cs-` token rather than a literal value.
4. Given a consumer that sets `--cs-lime: #00ff00` on `:root`, when a lime-toned component renders, then its resolved color is `#00ff00`.

## L2-006: Dark theme resolution

**Traces to:** L1-002

Applying the `.cs-theme-dark` class to any element must resolve the entire token set to the dark
FaithTech palette for that element and its descendants, and every component must remain legible and
contrast-compliant under it.

**Acceptance Criteria:**

1. Given `.cs-theme-dark` on a container, when any component renders inside it, then it uses dark-resolved tokens while components outside the container remain light.
2. Given nested `.cs-theme-light` inside `.cs-theme-dark`, when a component renders in the inner container, then it uses light-resolved tokens.
3. Given `.cs-theme-dark`, when contrast is measured for every text and icon element in the component gallery, then all pairs meet WCAG 2.2 AA (4.5:1 body text, 3:1 large text and non-text UI).
4. Given `.cs-theme-dark`, when the `color-scheme` property is read, then it resolves to `dark` so native controls and scrollbars adapt.

## L2-007: High-contrast and forced-colors support

**Traces to:** L1-002

Every component must remain usable under Windows High Contrast / `forced-colors: active`, retaining
visible boundaries, focus indication, and state differentiation without relying on removed
backgrounds or shadows.

**Acceptance Criteria:**

1. Given `forced-colors: active`, when any component with a background-only boundary renders, then a `1px` or greater border is applied so the boundary remains visible.
2. Given `forced-colors: active`, when a control receives keyboard focus, then a focus indicator using system colors is visible against the control.
3. Given `forced-colors: active`, when a selected, checked, or active state is applied, then the state is distinguishable by more than background color alone (border, mark, or text).
4. Given `forced-colors: active`, when an icon conveys meaning, then it retains a visible rendering via `forced-color-adjust` handling.

## L2-008: Reduced motion resolution

**Traces to:** L1-002

Every transition, animation, and auto-scrolling behavior must collapse to an instantaneous or
non-moving equivalent when `prefers-reduced-motion: reduce` is set, without removing the state
change itself.

**Acceptance Criteria:**

1. Given `prefers-reduced-motion: reduce`, when any component transitions state, then the computed transition and animation duration is `0s` or `1ms`.
2. Given `prefers-reduced-motion: reduce`, when an indeterminate progress indicator renders, then it presents a non-animated determinate-free state that still exposes `aria-busy` or an equivalent live status.
3. Given `prefers-reduced-motion: reduce`, when a component scrolls content programmatically, then the scroll uses `behavior: 'auto'` rather than `'smooth'`.
4. Given `prefers-reduced-motion: reduce`, when a dialog, drawer, toast, or menu opens, then it appears without translation or scale animation but still traps and restores focus identically.

## L2-009: Theme override contract and style encapsulation

**Traces to:** L1-002

Applications must be able to restyle the library entirely through public tokens and documented
public class hooks. A component must not require an application to write selectors targeting its
internal DOM structure, and no internal DOM structure is part of the public API.

**Acceptance Criteria:**

1. Given a component, when its template renders, then every element an application is documented to target carries a stable `cs-` prefixed class.
2. Given the documented public class list, when internal DOM structure changes in a patch release, then no documented public class is removed or repurposed.
3. Given an application that overrides only public tokens, when the component gallery renders, then a distinct visual theme is produced with zero `::ng-deep` and zero element-structure selectors in application styles.
4. Given a component, when its styles are inspected, then it declares no `!important` on any property an application is expected to override.

## L2-010: Typography system

**Traces to:** L1-002

The library must provide a typographic scale as both stylesheet classes and directives, covering
display headings, section headings, body, small/meta, eyebrow, monospace/code, accent scripture
quote, links, and truncation, with fluid responsive sizing and a readable prose measure.

**Acceptance Criteria:**

1. Given each documented typography level, when applied to an element, then `font-family`, `font-size`, `line-height`, `letter-spacing`, and `font-weight` all resolve from `--cs-` tokens.
2. Given viewport XS and viewport XL, when a display heading renders, then its computed font size differs and stays within the documented minimum and maximum bounds.
3. Given the prose style, when a paragraph renders at viewport LG, then its measure is between 45 and 85 characters.
4. Given a truncation directive with a single-line configuration, when text overflows, then it is clipped with an ellipsis and the full text remains available to assistive technology via an accessible name or title.
5. Given a document with no licensed FaithTech font available, when text renders, then the documented fallback stack applies without layout shift beyond the documented metric-adjusted tolerance.

## L2-011: CDK overlay usage

**Traces to:** L1-003

Every anchored or floating surface (menu, popover, tooltip, combobox listbox, dialog, drawer, toast
outlet, account menu, date picker panel) must be positioned by `@angular/cdk/overlay` with
collision-aware flexible connected positioning, scroll strategy, and backdrop configuration.

**Acceptance Criteria:**

1. Given an anchored surface near a viewport edge, when it opens, then CDK repositions it to remain fully within the viewport.
2. Given an open anchored surface, when the page scrolls, then the configured scroll strategy applies (reposition, block, or close) as documented for that component.
3. Given the library source, when it is scanned for manual positioning, then no component computes `getBoundingClientRect`-based placement outside CDK position strategies.
4. Given an open overlay, when the component is destroyed, then the overlay is disposed and no detached DOM node remains attached to the overlay container.

## L2-012: CDK focus and accessibility utilities

**Traces to:** L1-003

Focus trapping, focus restoration, focus monitoring, roving tabindex/active descendant list
management, live announcements, high-contrast detection, and unique ID generation must use
`@angular/cdk/a11y` primitives.

**Acceptance Criteria:**

1. Given a modal surface, when it opens, then a `ConfigurableFocusTrap` is active and Tab cycles only within the surface.
2. Given a modal surface, when it closes, then focus returns to the element that opened it.
3. Given a composite widget with roving focus (tabs, radio group, menu, segmented control, chip list, calendar grid), when arrow keys are pressed, then focus moves via `FocusKeyManager` or `ActiveDescendantKeyManager` semantics as documented for that widget.
4. Given a component that announces status, when the status changes, then the announcement is made through `LiveAnnouncer` or a component-owned live region documented in its accessibility notes.
5. Given any generated element ID, when two instances of the same component render, then their generated IDs are unique within the document.

## L2-013: CDK layout observation

**Traces to:** L1-003

Components with responsive structural changes must observe breakpoints through
`@angular/cdk/layout` `BreakpointObserver` rather than through window resize listeners.

**Acceptance Criteria:**

1. Given a component with responsive structure, when the viewport crosses a documented breakpoint, then the structural change occurs without a manual `window.resize` listener in the component source.
2. Given the library source, when it is scanned, then no component registers a `resize` listener on `window` except where a documented CDK gap is recorded in the source with a linked issue.
3. Given a server-side render, when a responsive component renders, then it emits its documented default (desktop-first or mobile-first as documented) without accessing `window`.

## L2-014: CDK text field, scrolling, and drag-drop usage

**Traces to:** L1-003

Autosizing textareas must use `@angular/cdk/text-field`; long virtualizable lists must offer
`@angular/cdk/scrolling` virtual scroll; drag-and-drop interactions must use `@angular/cdk/drag-drop`
with an accessible keyboard alternative.

**Acceptance Criteria:**

1. Given an autosize textarea, when the user types beyond the current height, then the element grows up to its configured maximum rows and then scrolls internally.
2. Given a list component configured for virtual scrolling with 10,000 items, when it renders, then the number of rendered DOM rows stays within the documented buffer bound.
3. Given a draggable item, when it is dragged with a pointer, then CDK drag-drop performs the transfer and emits a typed reorder or move intent.
4. Given a draggable item focused by keyboard, when the documented keyboard move sequence is used, then the same move intent is emitted and the result is announced to assistive technology.

## L2-015: No re-implementation of CDK behavior

**Traces to:** L1-003

The library must not contain hand-written implementations of focus traps, overlay positioning,
keyboard managers, scroll blocking, or drag-drop.

**Acceptance Criteria:**

1. Given the library source, when it is scanned for `document.addEventListener('keydown')` at module scope, then no such global listener exists outside a CDK-provided abstraction.
2. Given the library source, when focus-trap logic is searched for, then all trapping flows through `FocusTrapFactory` or `ConfigurableFocusTrapFactory`.
3. Given the library source, when scroll blocking is searched for, then body scroll locking flows through CDK `ScrollStrategyOptions.block()` and no component mutates `document.body.style.overflow` directly.

## L2-016: Standalone, signal-based, OnPush component contract

**Traces to:** L1-004

Every public component and directive must be standalone, must declare inputs via `input()` /
`input.required()` / `model()`, must declare outputs via `output()`, and must use
`ChangeDetectionStrategy.OnPush`. No public API uses decorator-based `@Input`/`@Output` or default
change detection.

**Acceptance Criteria:**

1. Given any public component, when its metadata is inspected, then `changeDetection` is `OnPush` and it is standalone.
2. Given any public component or directive, when its class members are inspected, then no `@Input()` or `@Output()` decorator is present.
3. Given any public component with state driven by inputs, when an input changes in a zoneless application, then the view updates without an explicit `markForCheck` call by the consumer.
4. Given the library source, when it is scanned, then no public component injects `ChangeDetectorRef` for the purpose of compensating for default change detection.

## L2-017: Naming, selector, and export conventions

**Traces to:** L1-004

Component selectors must use the `cs-` element prefix; directive selectors must use the `cs`
attribute camelCase prefix; every exported symbol must be prefixed `Cs`; every public symbol must be
re-exported from the package root.

**Acceptance Criteria:**

1. Given any public component, when its selector is read, then it matches `^cs-[a-z][a-z0-9-]*$`.
2. Given any public attribute directive, when its selector is read, then it matches `^\[cs[A-Z]` or a documented multi-selector containing such an attribute.
3. Given any symbol exported from `public-api.ts`, when its identifier is read, then it begins with `Cs`.
4. Given a public symbol declared in a `lib/` module, when the package root is imported, then that symbol is importable from `@quinntyne/cornerstone` directly.

## L2-018: Angular forms integration for value-bearing controls

**Traces to:** L1-004

Every value-bearing control must implement `ControlValueAccessor`, must support both reactive and
template-driven forms, must reflect `disabled` state from the form model, must propagate touched
state on blur, and must expose validation state visually and to assistive technology.

**Acceptance Criteria:**

1. Given a value-bearing control bound to a `FormControl`, when the user changes its value, then `control.value` updates and `control.dirty` becomes true.
2. Given a value-bearing control bound to a `FormControl`, when `control.disable()` is called, then the rendered control becomes non-interactive and exposes the disabled state to assistive technology.
3. Given a value-bearing control, when it loses focus, then `control.touched` becomes true exactly once per blur.
4. Given a value-bearing control with a failing validator and touched state, when it renders, then it sets `aria-invalid="true"` and references its error text via `aria-describedby`.
5. Given a value-bearing control bound with `[(ngModel)]`, when the model value changes programmatically, then the rendered value updates.

## L2-019: Field, label, and description wiring

**Traces to:** L1-004

Components must generate and wire their own `id`, `for`, `aria-labelledby`, `aria-describedby`, and
`aria-errormessage` relationships. Applications must never be required to author these attributes to
achieve a correct accessibility tree.

**Acceptance Criteria:**

1. Given a field wrapping a control with a label, hint, and error, when it renders, then the control's `aria-describedby` references both the hint and the error element IDs.
2. Given a field with a label, when the label is clicked, then focus moves to the wrapped control.
3. Given a field whose error is cleared, when it re-renders, then the removed error ID is no longer present in `aria-describedby`.
4. Given an application that supplies its own `aria-describedby` on the control, when the field renders, then the application value is preserved and the generated IDs are appended rather than replaced.

## L2-020: Content projection slot contract

**Traces to:** L1-004

Multi-slot components must expose named projection slots through documented `cs-*` selector
directives (for example `csCardHeader`, `csPageActions`, `csEmptyStateActions`), must render
slot-dependent chrome only when the slot has content, and must not require empty placeholder markup.

**Acceptance Criteria:**

1. Given a multi-slot component with no content in an optional slot, when it renders, then the wrapper element for that slot is absent from the DOM.
2. Given content projected into a named slot, when the component renders, then the content appears in the documented position and order.
3. Given projected content, when it is inspected, then it is projected once and not duplicated across responsive variants.
4. Given a documented slot directive, when it is applied to an element that is not a child of the owning component, then a developer-mode error naming the required parent is thrown.

## L2-021: Input coercion, defaults, and developer diagnostics

**Traces to:** L1-004

Inputs must apply documented defaults, must coerce boolean and numeric attribute forms, must reject
invalid enum values with a developer-mode error, and must not throw in production for recoverable
input mistakes.

**Acceptance Criteria:**

1. Given a boolean input written as a bare attribute, when the component renders, then the input resolves to `true`.
2. Given a numeric input supplied as a string attribute, when the component renders, then the input resolves to a `number`.
3. Given an invalid value for a documented enum input in development mode, when the component initializes, then an error naming the input and the allowed values is thrown.
4. Given the same invalid value in production mode, when the component initializes, then the documented default is used and rendering continues without throwing.
5. Given a required input that is omitted, when the application compiles, then compilation fails with an Angular required-input error.

## L2-022: Intent output contract for composites

**Traces to:** L1-004

Composite components must not perform HTTP calls, authorization decisions, persistence, workflow
enforcement, or navigation. They must accept a typed view model input and emit typed intent outputs.

**Acceptance Criteria:**

1. Given the library source, when it is scanned, then no component or directive injects `HttpClient`.
2. Given any composite, when the user performs an action, then the component emits a typed intent output and mutates no input object.
3. Given any composite bound to a frozen view model object, when the user performs every documented action, then no `TypeError` from mutation occurs.
4. Given any composite, when it is inspected, then it performs navigation only through a consumer-supplied `routerLink` binding or an emitted intent, never by injecting `Router` and calling `navigate` on its own initiative.

## L2-023: Public API surface stability report

**Traces to:** L1-004

The build must produce a checked-in public API surface report, and any change to that surface must
be an explicit, reviewed diff.

**Acceptance Criteria:**

1. Given a build, when it completes, then an API surface report listing every exported symbol with its full signature is generated.
2. Given a change that adds, removes, or alters a public signature without updating the checked-in report, when CI runs, then the build fails with a diff of the surface change.
3. Given a removal of a public symbol without a prior deprecation release, when CI runs, then the build fails citing L2-183.

## L2-024: Keyboard operability

**Traces to:** L1-005

Every interactive element must be reachable and fully operable by keyboard alone, with the standard
key bindings for its ARIA pattern, and must never create a keyboard trap outside an intentional
modal focus trap.

**Acceptance Criteria:**

1. Given any component, when the user tabs through it from the start of the document, then every interactive element is reachable in visual reading order.
2. Given any interactive element, when the documented keys for its ARIA Authoring Practices pattern are pressed, then the documented behavior occurs.
3. Given any non-modal component, when the user tabs past its last interactive element, then focus leaves the component.
4. Given any modal surface, when the user presses `Escape`, then the surface closes and focus returns to the trigger, unless the surface is documented as requiring an explicit decision.
5. Given a custom interactive element rendered from a non-interactive host tag, when it is inspected, then it carries an explicit `tabindex` and the correct `role`.

## L2-025: Visible focus indication

**Traces to:** L1-005

Every focusable element must present a focus indicator meeting WCAG 2.2 Focus Appearance, driven by
the `--cs-focus` token, applied on keyboard focus and not suppressed on pointer focus for elements
where pointer focus is meaningful.

**Acceptance Criteria:**

1. Given any focusable element, when it receives keyboard focus, then a focus indicator with at least a 2 CSS pixel perimeter and at least 3:1 contrast against adjacent colors is rendered.
2. Given any focusable element, when it receives focus, then the indicator is not clipped by an ancestor `overflow: hidden`.
3. Given the library source, when styles are scanned, then no rule sets `outline: none` without providing a replacement indicator in the same rule set.
4. Given a component inside `.cs-theme-dark`, when an element receives focus, then the indicator still meets the 3:1 contrast requirement.

## L2-026: Roles, names, states, and relationships

**Traces to:** L1-005

Every component must expose the ARIA role, accessible name, states, and relationships prescribed by
the ARIA Authoring Practices Guide pattern it implements, using native semantics where a native
element exists.

**Acceptance Criteria:**

1. Given any component, when its accessibility tree is computed, then its role matches the pattern named in its documentation.
2. Given any interactive element with only an icon, when its accessible name is computed, then a non-empty name is present, sourced from a required label input.
3. Given a component with selection, expansion, checked, pressed, busy, or current state, when that state changes, then the corresponding ARIA attribute updates in the same change detection cycle.
4. Given any component, when a native element exists for its semantics (`button`, `input`, `select`, `dialog`, `progress`, `table`), then the native element is used rather than a `div` with a role.

## L2-027: Live region and status announcement policy

**Traces to:** L1-005

Asynchronous state changes (loading, saved, error, offline, result counts, toast, validation
summary, drag-drop results) must be announced to assistive technology with a documented politeness
level, and must not announce redundantly.

**Acceptance Criteria:**

1. Given a component transitioning to a loading state, when the transition occurs, then a polite status is announced or `aria-busy="true"` is set on the labelled region.
2. Given an error alert, when it appears, then it is announced assertively exactly once.
3. Given a result set that changes from filtering or pagination, when the new count renders, then a polite announcement states the new count.
4. Given a component that announces status, when the same status value is set twice consecutively, then only one announcement is produced.

## L2-028: Color contrast and non-color state signalling

**Traces to:** L1-005

All text, icon, boundary, and state indication must meet WCAG 2.2 AA contrast, and no state is
conveyed by color alone.

**Acceptance Criteria:**

1. Given every documented component variant in light and dark themes, when contrast is measured, then body text meets 4.5:1, large text meets 3:1, and meaningful non-text elements meet 3:1.
2. Given any status, tone, or validation state, when it renders, then it is distinguishable by text, icon, or shape in addition to color.
3. Given a disabled control, when it renders, then it is visually distinct and exposes `disabled` or `aria-disabled` rather than relying on reduced contrast alone.

## L2-029: Automated accessibility verification gate

**Traces to:** L1-005

Every public component must have an automated accessibility test asserting zero violations for each
documented variant and state, and the build must fail on any violation.

**Acceptance Criteria:**

1. Given any public component, when the test suite runs, then an automated accessibility scan executes against every documented variant of that component.
2. Given a scan that reports a violation of serious or critical impact, when CI runs, then the build fails and names the component, rule, and element.
3. Given a public component with no accessibility test, when CI runs, then the coverage gate fails naming the component.
4. Given a component with documented keyboard behavior, when the test suite runs, then a test exercises each documented key binding.

## L2-030: Responsive breakpoint definition

**Traces to:** L1-006

The library must define and publish the breakpoint set XS (<576px), SM (>=576px), MD (>=768px), LG
(>=992px), XL (>=1200px) as tokens, Sass mixins, and a typed `CsBreakpoints` constant used by
`BreakpointObserver` integrations, and every responsive behavior in the library must key off this
set.

**Acceptance Criteria:**

1. Given the published breakpoint constant, when it is read, then it contains exactly the five documented breakpoints with the documented pixel values.
2. Given any component with responsive behavior, when its styles are inspected, then every media query threshold matches a published breakpoint value.
3. Given an application that imports the Sass mixins, when it writes a breakpoint mixin call, then the emitted media query matches the library's own thresholds.

## L2-031: Reflow, zoom, and touch targets

**Traces to:** L1-006

Every component must satisfy WCAG 2.2 Reflow at 320 CSS pixels width and 400% zoom, must avoid
two-dimensional scrolling except for content that legitimately requires it, and must present pointer
targets of at least 24x24 CSS pixels.

**Acceptance Criteria:**

1. Given a viewport of 320x256 CSS pixels, when any component renders, then no horizontal page scrolling is required to read content, except within a component documented as horizontally scrollable (table, kanban board, code block, timeline rail).
2. Given 400% zoom at a 1280px viewport, when any component renders, then all content and controls remain reachable and no content is clipped or overlapped.
3. Given any pointer target, when its rendered box is measured, then it is at least 24x24 CSS pixels, or spacing-exempt per WCAG 2.2 Target Size (Minimum).
4. Given a horizontally scrollable region, when it is rendered, then it is keyboard scrollable and exposes an accessible name and `tabindex="0"` where it is a scroll container.

## L2-032: Responsive verification harness

**Traces to:** L1-006

Every UI-facing component must be verified at all five viewport classes by automated tests, and
documented responsive transformations must be asserted rather than merely rendered.

**Acceptance Criteria:**

1. Given any public component, when the test suite runs, then it renders and asserts core behavior at XS, SM, MD, LG, and XL viewports.
2. Given a component documented to change structure at a breakpoint, when the viewport crosses that breakpoint, then a test asserts the documented structural difference.
3. Given a component with a mobile-specific affordance (sticky action bar, full-screen dialog, collapsed navigation, card-reflowed table), when tested at XS, then the affordance is asserted present and operable.

## L2-033: CsTheme provider and theme service

**Traces to:** L1-007

The library must expose a `CsTheme` provider function and service that registers the token layer,
reports the resolved theme (`light`, `dark`, `system`, `high-contrast`), allows an application to set
it, persists nothing on the user's behalf, and is safe to call during server-side rendering.

**Acceptance Criteria:**

1. Given the library source, when it is scanned, then no call to `bypassSecurityTrustHtml`, `bypassSecurityTrustScript`, `bypassSecurityTrustStyle`, `bypassSecurityTrustUrl`, or `bypassSecurityTrustResourceUrl` is applied to any consumer-supplied value.
2. Given any component receiving a string input, when that string contains `<script>alert(1)</script>` or an `onerror` attribute payload, then it renders as literal text and no script executes.
3. Given the library source, when it is scanned, then no component assigns to `innerHTML` or `outerHTML` with a consumer-supplied value.
4. Given a component that accepts SVG or icon markup, when markup is registered, then it is sanitized through Angular's sanitizer or restricted to a documented allowlist of elements and attributes.
5. Given a component rendering user-supplied text into a CSS custom property or inline style, when the value contains `url(` or `expression(`, then it is rejected or escaped and does not reach the style attribute unsanitized.

## L2-164: Safe link, URL, and target handling

**Traces to:** L1-019

Every component rendering a consumer-supplied URL must validate the scheme and apply safe target and
referrer handling.

**Acceptance Criteria:**

1. Given a URL with a `javascript:`, `data:`, or `vbscript:` scheme supplied to any link, image, media, or download input, when it renders, then the URL is rejected and the link is not navigable.
2. Given a link configured to open in a new tab, when it renders, then it carries `rel="noopener noreferrer"`.
3. Given an external link, when it renders, then its accessible name states that it opens externally.
4. Given any iframe rendered by the library, when it renders, then it carries an explicit `sandbox` attribute that excludes `allow-same-origin` together with `allow-scripts`, a required `title`, and a `referrerpolicy`.
5. Given a `mailto:` or `tel:` link, when it renders, then the value is encoded so that header-injection sequences cannot be introduced.

## L2-165: Dependency and supply-chain hygiene

**Traces to:** L1-019

The build must audit dependencies, pin them reproducibly, and block releases with known

**Acceptance Criteria:**

## L2-166: Release integrity and secret handling

**Traces to:** L1-019

The published package must carry verifiable provenance, must be built from the exact commit being
released, and must never expose credentials.

**Acceptance Criteria:**

1. Given a published version, when its npm metadata is inspected, then a provenance attestation referencing the source repository, workflow, and commit SHA is present.
2. Given the release workflow, when its definition is inspected, then the npm token is referenced only as a repository secret, is never echoed, and the job's permissions are the minimum required plus `id-token: write`.
3. Given the published tarball, when its contents are inspected, then it contains no `.env`, no token, no `.npmrc` with credentials, and no internal-only file.
4. Given any workflow log for a release, when it is inspected, then no secret value appears in plaintext.
5. Given the released tarball, when the build is repeated from the same commit, then the packaged output is byte-identical apart from documented timestamp fields.

## L2-167: Server-side rendering correctness

**Traces to:** L1-020

Every component must render on the server without accessing browser-only globals and must produce
complete, meaningful server HTML.

**Acceptance Criteria:**

2. Given a component with responsive or theme-dependent behavior, when it renders on the server, then it emits its documented server default without a runtime platform check failing.
3. Given a component with static content, when it renders on the server, then that content is present in the server HTML and is not deferred to the client.
4. Given the library source, when it is scanned, then every access to a browser global is guarded by `isPlatformBrowser` or is inside an `afterNextRender`/`afterRenderEffect` callback.

## L2-168: Hydration stability

## L2-170: No untranslatable embedded strings

**Traces to:** L1-021

Every user-visible string produced by the library must be either consumer-supplied or overridable

**Acceptance Criteria:**

2. Given an application that provides a translated localization token set, when every component renders, then every default string uses the provided translation.
3. Given the localization token set, when it is inspected, then every key is documented with its English default and the context in which it appears.

## L2-171: Right-to-left support

**Traces to:** L1-021

Every component must render and operate correctly under `dir="rtl"`.

**Acceptance Criteria:**

1. Given `dir="rtl"`, when any component renders, then its layout mirrors correctly and no content is clipped or overlapped.
2. Given the library styles, when they are scanned, then directional properties use logical equivalents (`margin-inline-start`, `padding-inline-end`, `inset-inline-start`, `text-align: start`) rather than physical left and right, except where a documented exception applies.
3. Given `dir="rtl"`, when arrow-key navigation is used in a horizontal widget, then `ArrowRight` moves toward the visual start and `ArrowLeft` toward the visual end.
4. Given `dir="rtl"`, when an anchored overlay opens, then CDK positions it using the correct directionality.
5. Given directional icons such as chevrons and back arrows, when `dir="rtl"` applies, then they are mirrored.

## L2-172: Locale-aware formatting

**Traces to:** L1-021

All dates, times, numbers, currencies, relative times, and pluralized strings must be formatted
through Angular's locale-aware mechanisms.

**Acceptance Criteria:**

1. Given a component displaying a date or time, when it renders under a non-English locale, then the value is formatted for that locale and the machine-readable value remains ISO-8601.
2. Given a component displaying a count, when the count is 0, 1, or many, then the pluralized string is selected through the localization mechanism rather than by string concatenation.
3. Given a component displaying a number or percentage, when it renders under a locale with different separators, then the separators match the locale.
4. Given the library source, when it is scanned, then no user-visible date, number, or plural string is produced by manual string concatenation.

## L2-173: Text expansion tolerance

**Traces to:** L1-021

## L2-174: Conventional commit enforcement

**Traces to:** L1-022

Commits and pull request titles that reach `main` must follow the Conventional Commits specification
so that version derivation is deterministic.

**Acceptance Criteria:**

2. Given a commit that lands on `main` whose subject does not match the format, when the release workflow runs, then it receives the patch fallback required by the every-push release policy.
3. Given the documented commit types, when the contribution guide is inspected, then each type is documented with the version bump it produces.
4. Given a commit with a `BREAKING CHANGE:` footer or a `!` marker, when versioning runs, then a major bump is derived.

## L2-175: Deterministic version derivation

**Traces to:** L1-022

The released version must be derived automatically from the conventional commits since the previous
release tag.

**Acceptance Criteria:**

1. Given commits since the last tag containing only `fix:` entries, when versioning runs, then a patch version is derived.
2. Given at least one `feat:` entry and no breaking change, when versioning runs, then a minor version is derived.
3. Given at least one breaking change, when versioning runs, then a major version is derived.
4. Given only `chore:`, `docs:`, `test:`, `ci:`, `style:`, or unclassified entries, when versioning runs, then a patch release is produced. The first release is `0.1.0`.
5. Given versioning runs twice on the same commit range, when both runs complete, then the derived version is identical.

## L2-176: Publish on push to origin main

**Traces to:** L1-022

A GitHub Actions workflow must publish `@quinntyne/cornerstone` and
`@quinntyne/cornerstone-design-system` at the same stable version to the public npm registry on every push to
the `main` branch of the `origin` remote, after the full verification suite passes.

**Acceptance Criteria:**

1. Given a passing push to `main`, including documentation-only changes, when the workflow completes, then both packages are available at the derived stable version with public access. Only the final commit of each push is released.
2. Given verification fails at any step, when the workflow runs, then the publish step does not execute and no version is published.
3. Given a push to a branch other than `main`, when the workflow evaluates its trigger, then the publish job does not run.
4. Given a pull request targeting `main`, when CI runs, then a publish dry run executes and reports the version that would be released without publishing it.
5. Given the workflow publishes, when the artifact is inspected, then it is the artifact produced by the same workflow run from the same commit SHA, not a rebuild.

## L2-177: Publish idempotency and concurrency

**Traces to:** L1-022

Releases must be idempotent and must never race.

**Acceptance Criteria:**

1. Given the derived version already exists on npm, when its source commit and tarball integrity match the durable release record, then it is verified and skipped. Conflicting content fails the run.
2. Given the workflow is re-run manually on the same commit, when it completes, then no duplicate publish is attempted and no error is raised.
3. Given two pushes to `main` in rapid succession, when both workflows run, then a concurrency group serializes them so that only one publish executes at a time and neither is cancelled mid-publish.
4. Given a publish fails partway, then its draft release record and exact tarballs remain available for repair; no final tag or public release is created until both packages verify. Later pairs wait for repair.

## L2-178: Tagging, changelog, and release notes

**Acceptance Criteria:**

2. Given a successful publish, then its GitHub release body records the included commits. Release automation creates no generated changelog or version commits on `main`.
3. Given a successful publish, when the GitHub releases page is inspected, then a release exists for the tag with the changelog section as its body.
4. Given a release containing a breaking change, when the release notes render, then a clearly marked breaking-changes section with migration guidance is present.
5. Given the changelog commit written back to `main`, when it lands, then it does not retrigger the release workflow.
