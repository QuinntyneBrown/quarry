# L1 - High-Level Requirements

Scope: the Cornerstone Angular UI library published as `@quinntyne/cornerstone`. Cornerstone extends
Angular CDK, implements the FaithTech Design System, and supplies every component listed in
[`docs/component-catalog.md`](../component-catalog.md) at a quality level equivalent to
[Angular Material](https://material.angular.dev/).

Terminology in this document follows RFC 2119 intent: "must" and "shall" state binding obligations.
Ambiguous modality ("should", "may", "might") is not used.

---

## L1-001: Distributable Angular library package

The library must be built and distributed as a single Angular Package Format (APF) library published
to the public npm registry under the name `@quinntyne/cornerstone`, consumable by any Angular application
without additional build configuration beyond installing the package and its peer dependencies.

## L1-002: FaithTech Design System token foundation

The library must express every visual decision (color, typography, spacing, radius, elevation,
motion, focus, and layout bounds) as public, documented, overridable design tokens derived from the
FaithTech Design System, and must provide light, dark, high-contrast, and reduced-motion resolutions
of those tokens.

## L1-003: Angular CDK behavior foundation

The library must build all focus management, overlay positioning, keyboard interaction, layout
observation, text autosizing, virtual scrolling, and drag-and-drop behavior on Angular CDK rather
than on hand-rolled equivalents, and must not re-implement behavior the CDK already provides.

## L1-004: Uniform component API contract

Every public component, directive, and service must conform to a single documented API contract
covering standalone declaration, signal-based inputs and outputs, `OnPush` change detection,
selector and symbol naming, content projection slots, input coercion, and Angular forms integration
for value-bearing controls.

## L1-005: Accessibility conformance

Every component must meet WCAG 2.2 Level AA, must be fully operable by keyboard alone, must expose
correct roles, names, states, and relationships to assistive technology, and must manage focus and
live-region announcements appropriately for its interaction pattern.

## L1-006: Responsive and adaptive behavior

Every UI-facing component must render and remain fully operable across extra-small (<576px), small
(>=576px), medium (>=768px), large (>=992px), and extra-large (>=1200px) viewports, and must satisfy
WCAG reflow at 320 CSS pixels width and 400% zoom without loss of content or function.

## L1-007: Foundations and layout suite

The library must supply the theme, icon, typography, container, layout primitive, page, section,
card, divider, toolbar, action bar, skip link, visually-hidden, and responsive-region capabilities
defined in catalog section 1.

## L1-008: Actions and form controls suite

The library must supply the button, icon button, button group, field, input, textarea, select,
checkbox, radio, switch, input group, search field, combobox, date and date-time field, file picker,
dropzone, choice card, form actions, validation summary, and wizard capabilities defined in catalog
section 2.

## L1-009: Navigation and shell suite

The library must supply the shell, topbar, sidenav, nav group, nav item, bottom navigation,
breadcrumbs, account menu, tab group, segmented control, menu, popover, accordion, paginator, and
marketing header/footer capabilities defined in catalog section 3.

## L1-010: Data display, status, and feedback suite

The library must supply the badge, pill, chip list, avatar, avatar stack, person, alert, offline
banner, toast, spinner, skeleton, empty state, state page, progress bar, progress ring, stat card,
KPI, list, definition list, table, responsive table, data toolbar, progress matrix, metric bars,
comparison chart, timeline, scripture quote, and tooltip capabilities defined in catalog section 4.

## L1-011: Overlays and transient interaction suite

The library must supply the dialog service and shell, confirm dialog, drawer, and unsaved-changes
dialog capabilities defined in catalog section 5, including CDK-backed focus trapping, focus
restoration, scroll management, and typed results.

## L1-012: Scheduling, communication, and content tools suite

The library must supply the calendar, event card, schedule list, message thread, message composer,
conversation list and item, notification list and item, announcement composer, media viewer,
attachment list, evidence preview, code block, code editor, and preview pane capabilities defined in
catalog section 6.

## L1-013: Learning, people, and operational workflow composites

The library must supply the learning journey, lesson step list, quiz, quiz question, quiz result,
assignment card, submission status, rubric, assessment editor, achievement card, badge collection,
person row, people directory, person summary, record tabs, attendance roster, attendance choice,
consent panel, CSV import wizard, curriculum tree and editor, progression builder, competency grid,
report filters, report dashboard, and audit log capabilities defined in catalog section 7. These
composites must accept view models and emit intents only.

## L1-014: Liturgy workflow suite

The library must supply domain-neutral process rail, process journey, gate, requirement checklist,
movement dial, movement list, pip strip, kanban board and column, work item card, phase lane,
project card, gratitude wall, and gratitude note capabilities defined in catalog section 8, with
Liturgy-specific vocabulary supplied through typed adapters rather than hard-coded labels.

## L1-015: Authentication and marketing compositions

The library must supply the auth layout, auth card, hero, content section, CTA section, logo mark,
and brand lockup capabilities defined in catalog section 9.

## L1-016: Documentation and API reference

The library must publish a documentation site presenting, for every public API, a live example, a
variant gallery, a generated API reference, accessibility notes, and copyable usage code, matching
the completeness of the Angular Material documentation site.

## L1-017: Verification, testing, and coverage

Every public API must be covered by automated unit, accessibility, and visual-regression tests, and
the build must fail when a public API lacks the required coverage or when any test regresses.

## L1-018: Performance and bundle efficiency

The library must be fully tree-shakeable, must impose bounded per-component bundle cost, and must
meet defined rendering and interaction latency budgets for large data-bearing components.

## L1-019: Security and supply-chain integrity

The library must render untrusted application-supplied content safely, must never introduce
injection or navigation vulnerabilities through its public API, and must publish with verifiable
provenance from a reproducible, dependency-audited build.

## L1-020: Server-side rendering and hydration safety

Every component must render correctly under Angular server-side rendering and must be compatible
with incremental hydration without hydration mismatch errors or direct access to browser-only
globals during server rendering.

## L1-021: Internationalization and locale safety

Every component must be localizable, must not embed untranslatable user-facing English strings, must
support right-to-left layout, and must handle dates, times, numbers, and pluralization through
locale-aware Angular mechanisms.

## L1-022: Versioning, release, and npm publication

The library must be versioned by semantic versioning derived from conventional commits, and every
push to the `main` branch of the `origin` remote must automatically build, verify, version, tag,
changelog, and publish the package to npm, idempotently and with provenance.

## L1-023: Support policy and compatibility

The library must declare and honor a documented support matrix for Angular versions, Node versions,
browsers, and deprecation timelines, and must provide automated migration schematics for breaking
changes.

## L1-024: Migration bridge for Liturgy and Word Up

The library must ship an opt-in compatibility stylesheet that preserves existing Liturgy and Word Up
markup during incremental migration, must document the audited component mapping, and must define
the conditions under which the bridge is removed.
