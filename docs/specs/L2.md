# L2 - Detailed Requirements

Status: Initial specification, 2026-09-10, based on the confirmed [L1 scope](L1.md), [project brief](../prompt.md), and [interactive mock](../mocks/README.md).

## Interpretation and verification conventions

The brief and `AGENTS.md` govern production scope. Mock data, sample counts, hand-authored vectors, and component samples are design references. They are not evidence that released libraries or production embeddings exist. Framework names used below are fixture identities, not claims about third-party packages.

Numeric limits, pagination, ordering tie-breaks, error contracts, freshness targets, and performance budgets below are baseline specification decisions introduced to make the confirmed L1 scope testable. They are not measured results or values attributed to the brief. Changing them requires updating these criteria and their acceptance tests together.

- **Page session:** the lifetime of the loaded Quarry page. Query, technology, results, and selection survive in-page details and preview interactions. A full reload starts with an empty query, all technologies, and no selection. No account or cross-device persistence is required.
- **UI viewport matrix:** 320 x 740 and 375 x 812 (XS, below 576 CSS px); 576 x 800 (SM); 768 x 1024 (MD); 992 x 800 (LG); 1200 x 900 and 1440 x 900 (XL). Also check widths 575, 767, 991, and 1199 at height 800 for breakpoint boundaries. All UI acceptance criteria inherit L2-024 through L2-027; run each UI flow at one size per band and the layout suite at every listed size.
- **Catalog fixture:** the eight illustrative entries from `docs/mocks/src/catalog.ts`, augmented with explicit patient/client record-table support on the practice entry and client-record inputs on the intake entry for production evaluation. Each fixture carries a stable ID, source metadata revision, actual component descriptors for its test harness, and a publication state. Additional fixtures isolate boundaries and faults. Keep production evaluation augmentation separate from the illustrative mock catalog; mock presentation fixes do not require freezing its source files.
- **Published:** validated metadata and usable framework information available to public discovery. A searchable revision additionally has a successfully generated compatible embedding. Draft, deleted, or withdrawn entries are never public recommendations.
- **Evaluation queries:** `Animal Hospital`; `I want to build a veterinary clinic application`; `Online store`; `Analytics dashboard`; `A pet care practice with booking, client records, and intake forms`; and `xyzzy unrecognized project`. Expected capability judgments are specified in L2-006. Tests must not add the first two query phrases to catalog names or descriptions to force literal matches.
- **Ranking configuration:** a frozen embedding model/version, input construction, similarity metric, and relevance threshold. Use cosine similarity with a calibrated threshold recorded with the model version. The threshold must satisfy L2-006 and must not be copied from the mock's hand-authored vector scale. Backend acceptance fixtures can inject known vectors and scores to test deterministic ordering; production retrieval evaluation must use the configured real embedding model.
- **Verification layers:** Playwright tests use Page Objects and shared API fixtures; API acceptance tests verify real HTTP behavior and SQL persistence in an isolated test database; retrieval evaluation uses actual embeddings; framework consumer checks exercise built packages. Implementation constraints and ATDD evidence are reviewed directly. Never test architecture by asserting physical file or folder placement.

## L2-001: Project search entry and explicit submission
**Traces to:** L1-001

Quarry shall lead with a labeled project-description field and a `Find frameworks` submit action. Editing shall remain separate from submitting.

**Acceptance Criteria:**
1. Given a fresh page session, when the page loads, then the project-search heading, labeled field, submit action, and catalog-browse content are present, with search preceding the catalog in reading and tab order.
2. Given an entered project description, when the user presses Enter in the field or activates `Find frameworks`, then Quarry submits the trimmed description and displays that submitted description with its results.
3. Given results for query A, when the user edits the field to query B without submitting, then results remain associated with A and no semantic-search request for B is sent.
4. Given an empty or whitespace-only submitted field, when submission completes, then Quarry enters browse mode without requesting a query embedding.

---

## L2-002: Project examples and search shortcut
**Traces to:** L1-001

Quarry shall offer the three project examples shown in the mock and a keyboard shortcut to focus search.

**Acceptance Criteria:**
1. Given the discovery page, when the user activates `Animal Hospital`, `Online store`, or `Analytics dashboard`, then the field receives that exact text and the query submits using the current technology filter.
2. Given focus outside a detail dialog, when the user presses Ctrl+K or Cmd+K, then focus moves to the project field without submitting or clearing it.
3. Given an open detail dialog, when the shortcut is pressed, then focus remains within the dialog and the search field is unchanged.
4. Given any viewport in the UI matrix, when the example controls wrap, then all three remain readable, reachable, and operable without horizontal page scrolling.

## L2-003: Validated framework metadata
**Traces to:** L1-002

Each catalog entry shall have a stable unique ID, name, description, technology, nonempty descriptive tags, capabilities, suitable use cases, and component descriptors. Component counts shall be derived from those descriptors. Metadata shall use supported facts and shall persist with a revision identifier.

**Acceptance Criteria:**
1. Given a valid entry, when an authorized maintenance operation saves it and public discovery reads its published revision, then its identity, metadata, and component count agree across catalog, recommendation, and detail responses.
2. Given an entry with a blank required field, no tags, no capabilities, no use cases, duplicate component IDs, or duplicate framework ID on creation, when saving is attempted, then it fails with field-level validation and the previous stored entry is unchanged.
3. Given the baseline technology values React, Angular, Vue, and Web Components, when a valid entry uses one, then its published technology is preserved; an unsupported value fails validation.
4. Given proposed capability statements and component descriptors, when an entry is approved for publication, then the maintainer records evidence from that framework's documentation or working examples; illustrative mock claims alone do not qualify as production evidence.

---

## L2-004: Public catalog and detail API behavior
**Traces to:** L1-002

The API shall expose published catalog entries, metadata, and framework details with stable identities and bounded pages. Responses shall distinguish unavailable entries from unavailable services.

**Acceptance Criteria:**
1. Given a published framework ID, when its details are requested, then the API returns HTTP 200 with that entry's metadata, component descriptors, and revision.
2. Given an unknown, draft, deleted, or withdrawn ID, when public details are requested, then the API returns HTTP 404 without exposing unpublished metadata.
3. Given catalog pages, when each response is read, then it identifies returned entries, the filtered total, and whether a next page exists; a page contains at most 24 entries.
4. Given a catalog dependency failure, when a request cannot complete, then the API returns HTTP 503 with a safe error code and correlation ID, rather than HTTP 200 with an empty catalog.

---

## L2-005: Real semantic embeddings and vector retrieval
**Traces to:** L1-003

Production search shall generate embeddings from framework descriptions and tags and from the submitted query using a compatible embedding model. It shall retrieve by vector similarity. Hard-coded query-to-framework mappings shall not fulfill this requirement.

**Acceptance Criteria:**
1. Given published searchable metadata and a nonempty valid query, when retrieval runs, then the configured embedding integration processes the query and compares it with embeddings generated from catalog descriptions and tags.
2. Given two catalogs differing only in a description or descriptive tag, when the changed entry is reindexed, then the embedding input contains the changed text and its recorded source revision changes.
3. Given the configured production model, when retrieval evaluation runs, then it meets L2-006 using actual generated vectors without mock intent mappings or injected ranking scores.
4. Given vectors with incompatible model versions or dimensions, when retrieval attempts to use them, then they are excluded from comparison and index health records the incompatibility; the service never silently compares incompatible vectors.

---

## L2-006: Semantic relevance evaluation
**Traces to:** L1-003

The release evaluation shall verify meaning-based discovery and rejection of irrelevant matches using a frozen catalog and ranking configuration. Expected matches shall be judged by supported capabilities.

**Acceptance Criteria:**
1. Given the evaluation catalog and either `Animal Hospital` or `I want to build a veterinary clinic application`, when searching all technologies, then the top three entries are the practice, booking, and intake fixtures, with the practice fixture first. Their metadata collectively supports scheduling, intake, patient/client record interfaces, and practice operations.
2. Given `A pet care practice with booking, client records, and intake forms`, when searching all technologies, then the top three include the practice and intake fixtures, despite the full sentence being absent from catalog text.
3. Given `Online store`, when searching, then the commerce fixture ranks first and its explanation mentions supported product, cart, or checkout components; given `Analytics dashboard`, when searching, then the analytics fixture ranks first with an explanation grounded in charts, metrics, tables, or reporting.
4. Given `xyzzy unrecognized project`, when searching, then no result exceeds the calibrated relevance threshold and an empty result is returned.
5. Given a proposed model, metadata, or threshold change, when release evaluation runs, then all these judgments pass and the report records catalog revision, model version, threshold, query, returned IDs, and order. Evaluation uses synthetic queries only.

---

## L2-007: Recommendation limits and deterministic ranking
**Traces to:** L1-003

Search shall return at most three qualifying recommendations for the current query and technology, ordered by descending cosine similarity. This limit adopts the mock's focused presentation as a baseline decision. Equal scores shall be ordered by stable framework ID using ordinal ascending order.

**Acceptance Criteria:**
1. Given injected candidate similarities above, equal to, and below threshold T, when retrieval runs, then candidates at or above T are eligible and candidates below T are excluded.
2. Given five eligible candidates, when retrieval completes, then the three highest-ranked candidates are returned once each with contiguous display ranks 1 through 3.
3. Given candidates with equal scores and the same catalog and ranking configuration, when the same search repeats, then ties always follow ascending stable ID order.
4. Given zero, one, or two eligible candidates, when retrieval completes, then exactly that number is returned without padding with irrelevant frameworks.

---

## L2-008: Searchable metadata refresh
**Traces to:** L1-003

Search indexing shall track source revisions, refresh changed descriptions and tags, and prevent obsolete revisions from overwriting newer work. The healthy-service freshness target is 60 seconds after an accepted metadata change.

**Acceptance Criteria:**
1. Given healthy dependencies and an accepted searchable metadata change, when 60 seconds elapse, then new searches use the refreshed compatible embedding and current metadata revision.
2. Given revision B accepted after A, when indexing A finishes after B, then A cannot replace B's searchable representation.
3. Given an entry whose metadata changed but whose refreshed embedding is not ready, when searching, then that entry is excluded from semantic results and the response indicates that results are temporarily incomplete. Browsing and details still show its latest published metadata.
4. Given a withdrawn or deleted entry, when a new search begins after that change is accepted, then the entry is excluded even if its previous vector still exists.
5. Given a failed index refresh, when the dependency recovers and retry succeeds, then the current revision becomes searchable and the incomplete-results condition clears without manual metadata re-entry.

---

## L2-009: Empty-query browsing and catalog pagination
**Traces to:** L1-004

Browse mode shall show published entries ordered by case-insensitive ordinal name, then stable ID. It shall load 24 entries initially and expose `Load more` only when another page exists.

**Acceptance Criteria:**
1. Given an empty query and the eight-entry fixture, when browsing all technologies, then all eight entries appear without relevance ranks or query-specific explanations.
2. Given 25 matching entries, when browse mode loads, then 24 entries and `Load more` appear; when it is activated, then the last entry is appended and the control disappears.
3. Given a stable catalog revision, when all pages are loaded, then every matching entry appears exactly once in the specified order and the displayed total equals the filtered total.
4. Given a catalog revision change between page requests, when the next page is requested, then the client restarts that browse list against the new revision with a catalog-updated notice, preserving query, technology, and selection rather than combining incompatible pages.

---

## L2-010: Technology filtering preserves relevance
**Traces to:** L1-004

Quarry shall provide `All technologies`, React, Angular, Vue, and Web Components as the baseline filter values. Filtering shall apply to eligible candidates before the three-result limit.

**Acceptance Criteria:**
1. Given a submitted query, when technology changes, then results contain only that technology and retain the query; their relative relevance order matches the same candidates' unfiltered similarity order.
2. Given four eligible candidates where an eligible React entry ranks fourth overall, when the user selects React, then that entry is considered for the filtered top three despite absence from the initial result list.
3. Given an empty query, when technology changes, then the browse list and total update to matching entries in browse order and pagination restarts.
4. Given filtered results, when `All technologies` is selected, then the unfiltered top three or browse list returns using the current query; any selected framework remains selected even if it is outside the filter.

---

## L2-011: Clear search and reset discovery
**Traces to:** L1-004

`Clear search` shall clear draft and submitted queries while retaining technology. `Browse all frameworks` shall clear both queries and reset technology to `All technologies`. Neither action shall clear selection.

**Acceptance Criteria:**
1. Given a submitted query, an edited draft, and a technology filter, when `Clear search` is activated, then both queries become empty, filtered browse results appear, and focus returns to the search field.
2. Given an active query or filter, when `Browse all frameworks` is activated, then the query is empty, all technologies are selected, and the initial browse page appears.
3. Given a selected framework, when either reset action runs, then the selection summary retains that framework.
4. Given a slow search request, when discovery is cleared or reset before it completes, then its later response cannot restore the old query or replace the reset browse results.

---

## L2-012: Honest empty states
**Traces to:** L1-004

Valid zero-match responses shall explain that no matching frameworks were found for the current search or filter and offer query revision, technology changes, and a full browse reset.

**Acceptance Criteria:**
1. Given a completed query with zero eligible matches and a complete healthy index, when results render, then no cards appear and a no-matches message with `Browse all frameworks` is shown alongside usable query and technology controls.
2. Given a query whose candidates all fail the technology filter, when results render, then the active technology remains visible and changing it can recover results without re-entering the query.
3. Given an empty published catalog, when browsing succeeds, then the page states that no frameworks are available and does not suggest an API failure or fabricate sample entries.
4. Given an incomplete index or failed search, when there are no returned entries, then Quarry shows the indexing or service condition defined in L2-036 instead of claiming that no relevant frameworks exist.

---

## L2-013: Recommendation cards and result context
**Traces to:** L1-005

Each recommendation card shall show the framework name, description, descriptive tags, technology, component count, rank, explanation, and an action to inspect details.

**Acceptance Criteria:**
1. Given a successful search response, when the page renders it, then each card exposes all required fields from that result revision and its detail action identifies the framework accessibly.
2. Given three returned recommendations, when their heading renders, then it identifies the submitted query, reports three recommendations, and states that they are ordered by relevance.
3. Given a selected framework in the result list, when its card renders, then a textual selected indicator appears in addition to styling.
4. Given long descriptions, tags, and framework names across the UI matrix, when cards render, then text wraps without obscuring technology, rank, or the detail action.

---

## L2-014: Capability-grounded explanations
**Traces to:** L1-005

Explanations shall connect the requested project to recorded capabilities. They shall carry supporting capability references in the API response, enabling validation without requiring a generative explanation model.

**Acceptance Criteria:**
1. Given a recommendation with a scheduling capability, when it explains relevance to a practice query, then the explanation identifies that scheduling support and references the supporting capability in the same framework revision.
2. Given the veterinary evaluation queries, when cards and details render, then their explanations describe UI support without claiming a complete veterinary system, diagnosis, clinical safety, or regulatory compliance.
3. Given an explanation referencing a nonexistent capability, when the response is assembled, then it is replaced with factual wording based on existing metadata; unsupported claims are not delivered to the user.
4. Given any recommendation, when it renders, then no similarity score is labeled as a confidence percentage or probability of suitability.

---

## L2-015: Framework details and tabs
**Traces to:** L1-006

The detail view shall provide Overview and Components tabs, framework metadata, a theme explanation, and selection controls.

**Acceptance Criteria:**
1. Given a framework card, when its detail action is activated, then a labeled modal opens on Overview showing that framework's name, description, technology, tags, component count, capabilities, and use cases.
2. Given details opened from a recommendation, when Overview appears, then it includes the explanation associated with that query and framework revision; browse-origin details do not invent a query-specific explanation.
3. Given the open modal, when Components is activated, then the preview content replaces Overview and the selected tab and panel relationship update accessibly.
4. Given details fail to load or the entry returns 404, when the modal renders, then it shows an unavailable state, offers retry only for retryable failure, retains a close action, and disables selecting that unavailable entry.
5. Given a recommendation based on revision A and details returning newer revision B, when the modal renders, then it identifies that framework information was updated, displays B's metadata, and omits A's explanation unless a replacement grounded in B is available; closing details still preserves the current discovery state.

---

## L2-016: Interactive and isolated component previews
**Traces to:** L1-006

Production previews shall demonstrate documented components from the identified framework. The baseline interactive sample shall include a labeled text input, switch, save feedback, and reset behavior. Generic stand-ins shall be labeled as illustrative and shall not be accepted as proof of released components.

**Acceptance Criteria:**
1. Given the baseline fixture preview, when the user changes `Display name` from Jamie to Alex, toggles `Email notifications`, and activates `Save changes`, then the input and switch reflect the new state and a status message says the changes were saved for Alex in the preview.
2. Given an edited preview, when `Reset` is activated, then the name returns to Jamie, notifications are enabled, and a reset status appears; a blank saved name produces feedback addressed to `you`.
3. Given any preview edit or save, when requests and discovery state are observed, then no catalog mutation, email, external account action, or selection change occurs.
4. Given a released framework entry, when its preview is verified, then the working controls are traceable to that framework's component descriptors and build; a generic control relabeled with the framework's name fails this verification.
5. Given preview initialization or execution failure, when it occurs, then an inline preview-error state offers retry while Overview, close, and selection for an otherwise available framework remain usable.

---

## L2-017: Detail exit and discovery-state restoration
**Traces to:** L1-006

Closing details shall preserve discovery state and restore focus. Reopening a preview shall start with its default local state.

**Acceptance Criteria:**
1. Given a submitted query, draft edit, technology filter, result order, loaded browse pages, and selection, when details are opened and closed, then all those values and the discovery scroll position are retained.
2. Given an open detail modal, when the user activates Close, presses Escape, or clicks the backdrop outside the modal, then it closes and focus returns to its opener; clicking inside the modal does not dismiss it.
3. Given an opener removed by a catalog refresh, when details close, then focus moves to the result heading, which must be programmatically focusable, without resetting search.
4. Given modified preview controls, when details close and reopen, then the preview uses its default input, switch, and feedback state.

---

## L2-018: Select and review one framework
**Traces to:** L1-007

Quarry shall retain zero or one selected framework by stable ID during the page session and provide a persistent summary with its name, technology, review action, and clear action.

**Acceptance Criteria:**
1. Given no selection and available framework details, when `Select <name>` is activated, then that ID becomes selected, the button reads `Selected`, a status announces selection, and the summary identifies that framework.
2. Given a selected framework, when the user searches, filters, resets discovery, or closes details, then the summary continues to identify it even when its card is absent.
3. Given the summary, when its review action is activated, then details open for the selected ID and show its selected state; any recommendation explanation shown must match the current query and revision.
4. Given a full page reload, when the new session starts, then there is no selection, the query is empty, and technology is `All technologies`.

---

## L2-019: Replace, clear, and reconcile selection
**Traces to:** L1-007

Selecting another framework shall replace the previous selection. Explicitly clearing selection shall preserve discovery state. Known unavailable selections shall be identified honestly.

**Acceptance Criteria:**
1. Given selected framework A, when available framework B is selected, then only B appears selected in the summary, cards, and details, without a multi-selection or confirmation step.
2. Given selected framework A, when its already-selected button is activated again, then A remains the only selection.
3. Given a selection, when `Clear selected framework` is activated, then the summary disappears, selected indicators clear, and a no-selection status is announced while query, technology, and results remain unchanged. Focus moves to the selected card's detail action if present, otherwise to the result heading.
4. Given a selected ID that later returns 404 during review or refresh, when that response arrives, then the summary marks it unavailable and offers clearing or replacing it; the client does not substitute another framework automatically.

---

## L2-020: Framework theming and skins
**Traces to:** L1-008

Each framework shall document and expose customization for theme colors and skin styling through its independently usable design system.

**Acceptance Criteria:**
1. Given a built framework in a consumer application, when a consumer supplies custom brand, background, foreground, and border colors through its documented theme interface, then representative input, button, and surface components render those overrides without source edits to the library.
2. Given a consumer skin overriding typography, spacing, and border treatment through documented customization, when the same components render, then those settings apply and their input, focus, and activation behavior still works.
3. Given the independently built design-system output, when the consumer loads it without Quarry's API or browsing app, then its documented tokens and theme styles remain usable.

---

## L2-021: Appearance-independent discovery and selection
**Traces to:** L1-008

Discovery shall explain implementation-time customization and exclude color-oriented ranking and controls.

**Acceptance Criteria:**
1. Given the discovery page or any framework details, when displayed, then a short note explains that every framework supports custom themes and skins during implementation.
2. Given the full search-to-selection flow at any supported viewport, when the user completes it, then there are no palette galleries, swatches, color filters, preset-color comparisons, design-token selection tabs, or color-selection steps.
3. Given identical searchable descriptions, tags, query, and model configuration, when only example presentation colors or skin assets change, then embedding inputs, relevance scores, result order, and selection eligibility remain unchanged.

---

## L2-022: Independent framework build, test, and consumption
**Traces to:** L1-009

Each framework shall provide documented commands to build, test, package, and consume its library independently. Framework implementation technology shall not be dictated by the Quarry frontend.

**Acceptance Criteria:**
1. Given one framework's source and declared dependencies with Quarry and other frameworks unavailable, when its documented build, unit tests, and package commands run, then they succeed without starting or contacting Quarry's API.
2. Given its built package and documented runtime prerequisites, when installed in a minimal compatible consumer, then representative components render and respond to interaction with all Quarry endpoints blocked.
3. Given a release candidate for one framework, when its release validation executes, then its package version and validation outcome can be produced independently of another framework's release status.

---

## L2-023: Framework companion applications and evidence
**Traces to:** L1-009

Each framework shall provide companion applications and supporting documentation as their content is delivered, following the responsibilities in `AGENTS.md`.

**Acceptance Criteria:**
1. Given a delivered component, when its documentation example and manual development harness are opened using documented commands, then both render it and permit its documented interactions without Quarry's backend.
2. Given the deterministic acceptance harness, when the same component scenario repeats with the same fixtures, then its observable state and interaction outcome are consistent and do not depend on live external services.
3. Given a framework marketing application with delivered content, when it builds and runs independently, then framework information and links to its documentation work without the Quarry browsing app.
4. Given a component release, when its supporting evidence is reviewed, then component behavior is covered by unit and browser scenarios, documented requirements and designs explain the delivered behavior, and any published performance claim has a reproducible benchmark. Empty placeholder applications or speculative benchmarks are not required.

---

## L2-024: Responsive layouts for every UI flow
**Traces to:** L1-010

Discovery and modal layouts shall adapt across the entire UI viewport matrix. XS and SM use one card column, MD uses two, and LG and XL use three.

**Acceptance Criteria:**
1. Given each listed viewport and a populated catalog, when browsing and search results render, then the specified column count is used and document scroll width does not exceed viewport width by more than one CSS pixel.
2. Given XS or SM widths, when search renders, then the submit action occupies its own full-width row and examples wrap; at all widths, the technology control and all labels remain reachable.
3. Given details, Components, loading, empty, and error states at every listed viewport, when the user interacts, then content fits the viewport width and all close, retry, preview, and selection controls can be reached through vertical scrolling.
4. Given a visible selection summary, when the bottom of the catalog is scrolled into view, then the last card and its actions can be fully exposed above the summary; no fixed element prevents activation.

---

## L2-025: Keyboard navigation and modal focus
**Traces to:** L1-010

Every discovery control shall be usable by keyboard with visible focus and logical navigation. Details shall constrain focus until dismissed.

**Acceptance Criteria:**
1. Given only keyboard input, when the user submits an example or query, filters, opens details, interacts with preview controls, selects, reviews, replaces, and clears selection, then every action is achievable without pointer input and focus is visible throughout.
2. Given the first focusable page element, when Tab is pressed from the browser's page entry, then the skip link becomes visible; activating it moves focus to the catalog's programmatically focusable heading or container.
3. Given an opened detail modal, when it appears, then focus moves to its close button and subsequent Tab/Shift+Tab navigation stays within the modal; background controls cannot be activated until dismissal.
4. Given focus on a detail tab, when Left/Right Arrow, Home, or End is pressed, then Left/Right cycles between Overview and Components, Home selects Overview, End selects Components, and focus and active panel move together.

---

## L2-026: Accessible names, roles, and status updates
**Traces to:** L1-010

Controls, results, tabs, dialogs, switches, and status messages shall expose meaningful semantics to assistive technology.

**Acceptance Criteria:**
1. Given the discovery accessibility tree, when controls are inspected, then search and technology have associated labels; icon-only clear, review, and close actions have names; each card identifies its framework; and the dialog has the framework detail heading as its accessible name.
2. Given detail tabs and a preview switch, when their state changes, then selected-tab, controlled-panel, and checked-state semantics reflect the visible state.
3. Given search completion, failure, selection change, or preview feedback, when it occurs, then a live status or alert announces the outcome once without forcing focus away from the user's control.
4. Given form validation errors, when submission fails, then the relevant field exposes invalid state and an associated error message, and keyboard and assistive-technology users can locate the error.

---

## L2-027: Readability, target size, zoom, and reduced motion
**Traces to:** L1-010

Quarry shall preserve readability and operation under zoom and motion preferences. These criteria are explicit baseline checks rather than a claim of formal accessibility certification.

**Acceptance Criteria:**
1. Given normal text and its rendered background, when contrast is measured, then the ratio is at least 4.5:1; text at least 24 CSS px or bold text at least 18.66 CSS px has a ratio of at least 3:1.
2. Given interactive boundaries, state indicators, and focus indicators, when compared with adjacent colors, then their distinguishing visual information has at least 3:1 contrast, and selected state is also expressed in text or semantics.
3. Given pointer controls throughout the UI, when their hit areas are measured, then each is at least 24 by 24 CSS px; given 200% browser zoom on a 1280 x 900 window, when each flow is completed, then text and controls remain available without clipping or two-dimensional page scrolling.
4. Given reduced-motion preference, when search, selection, or modal state changes, then nonessential animations and smooth scrolling are disabled without changing the outcome.

---

## L2-028: Public discovery and protected maintenance
**Traces to:** L1-011

Public read operations shall work without sign-in. Public users shall have no catalog or index mutation authority. This requirement does not introduce an administrative UI.

**Acceptance Criteria:**
1. Given no credentials, when catalog, search, and available details are requested and a framework is selected locally, then the flow works without a login prompt or authentication cookie.
2. Given an exposed HTTP maintenance operation and no credentials, when a catalog or index mutation is attempted, then it returns HTTP 401 and leaves state unchanged; valid credentials without the required maintenance permission return HTTP 403 with unchanged state.
3. Given valid authorized maintenance credentials, when a valid supported update is executed, then the update succeeds and its actor identity, target ID, revision, and outcome are auditable without recording credential material.
4. Given maintenance is provided only through an offline command, when its access is reviewed, then execution and database write credentials are restricted to the maintenance service identity or authorized operator; public API credentials have no path to perform the command.
5. Given cookie-authenticated maintenance if that mechanism is used, when a cross-site mutation lacks a valid anti-forgery token, then it is rejected without state changes.

---

## L2-029: Input validation and injection resistance
**Traces to:** L1-011

The API shall enforce input limits independently of browser checks and treat queries, metadata, and preview input as untrusted data. Queries shall be limited to 500 UTF-16 code units after trimming, matching the browser field's counting convention.

**Acceptance Criteria:**
1. Given query lengths 0, 1, 500, and 501 after trimming, when submitted directly to the API, then 0 enters browse mode, 1 and 500 are accepted, and 501 returns HTTP 400 with a field error before embedding work begins; the browser prevents typing beyond its 500-unit limit.
2. Given malformed request data, an unsupported technology, a malformed or filter-incompatible cursor, or a requested page size outside 1 through 24, when sent to the API, then it returns HTTP 400 with a stable error code and no database mutation or embedding request. Request bodies over 16 KiB return HTTP 413 before processing. Pagination uses the cursor contract in the catalog design; page-number parameters are unsupported and return HTTP 400.
3. Given query, catalog, or preview text containing script tags, HTML attributes, or SQL syntax, when accepted text is displayed or searched, then it remains inert text, executes no script, and changes no database records.
4. Given a query that instructs the system to ignore rules, reveal secrets, or recommend unsupported capabilities, when processed, then it is treated only as search data, grants no tool or maintenance access, and cannot override explanation grounding.

---

## L2-030: Data protection and integration boundaries
**Traces to:** L1-011

Production transport and integrations shall protect user queries and service credentials. Query history shall not be persisted by Quarry; search text shall stay out of URLs, routine telemetry, and browser persistent storage.

**Acceptance Criteria:**
1. Given a production deployment, when the browser submits a query, then it uses HTTPS with query text in the request body, and no query is added to navigation URLs, persistent browser storage, or application query-history tables.
2. Given successful and failed searches containing a unique synthetic sensitive marker, when routine logs, traces, metrics labels, and error responses are inspected, then the marker is absent; operational records contain correlation IDs and aggregate measurements instead.
3. Given an embedding integration, when request contents are inspected using synthetic data, then only necessary query text or catalog embedding input is sent to the configured destination; browser credentials, secret configuration, preview input, and unrelated user data are absent.
4. Given an external embedding provider, when production configuration is reviewed, then the provider and its documented retention setting are recorded and the UI discloses external processing before submission. Unsupported retention assumptions cannot be represented as guarantees; a locally hosted model needs no external-processing notice.
5. Given browser assets, public API errors, and preview execution, when inspected, then no database or embedding-service secret is exposed. Untrusted preview code cannot read parent-page credentials, navigate the top-level page, or call maintenance services; any sandbox permissions granted must be limited to the preview's documented interactions.

## L2-031: Request quotas and overload responses
**Traces to:** L1-011

The baseline service shall enforce per-client quotas of 30 semantic searches and 120 catalog/detail reads per 60-second fixed window. Quotas shall be configurable and use the trusted connection address, not arbitrary client-supplied forwarding headers.

**Acceptance Criteria:**
1. Given a fresh window for one client, when it submits 30 valid semantic searches followed by a 31st, then the first 30 pass quota admission and the 31st returns HTTP 429 with `Retry-After` equal to the remaining whole seconds rounded up; rejected requests do not invoke embeddings.
2. Given 120 catalog/detail reads in one window, when the next read arrives, then it returns HTTP 429; after the window boundary, admission resumes independently of the search quota.
3. Given spoofed forwarding headers from an untrusted proxy, when requests arrive, then those headers cannot create new client identities or bypass the quota.
4. Given HTTP 429 in the UI, when displayed, then it explains the temporary limit, retains the current query/filter/selection, and enables an explicit retry after the indicated delay without automatic retry loops.

## L2-032: Measurable latency and workload baseline
**Traces to:** L1-012

Performance shall be measured against 1,000 published, fully indexed frameworks with descriptions up to 2,000 characters and up to 20 tags each. The API and database benchmark allocation is 4 vCPU and 8 GiB RAM combined; embedding-model hardware or hosted provider configuration, browser version, and network profile shall be recorded separately. Use 20 distinct admitted clients, a two-minute warm-up, and a ten-minute measured run at 10 requests/second: 60% catalog reads, 20% details, and 20% semantic searches, distributed evenly across clients with varied uncached queries.

**Acceptance Criteria:**
1. Given that benchmark and healthy dependencies, when latency is measured from HTTP receipt to response completion, then catalog/detail p95 is at most 500 ms, semantic-search p95 including embedding work is at most 3 seconds, and at least 99% of admitted valid requests return successful responses.
2. Given a production browser build at 10 Mbps download, 2 Mbps upload, 100 ms round-trip latency, and fourfold CPU throttling, when a fresh browse page is opened 20 times, then the p95 time from navigation to usable search controls and first browse cards is at most 3 seconds.
3. Given already-loaded data and the same browser profile, when detail tabs, preview controls, or local selection are changed 20 times each, then their p95 input-to-visible-feedback latency is at most 100 ms.
4. Given a performance report, when reviewed, then it records the defined workload, all environment settings, p95 values, success counts, and embedding configuration; measurements made with a stub are labeled and cannot satisfy the real semantic-search budget.

## L2-033: Bounded search work and deadlines
**Traces to:** L1-012

Each API instance shall admit at most 16 simultaneous semantic searches, perform no unbounded request queuing, and bound dependency waits. The embedding deadline is 5 seconds and the API search deadline is 8 seconds.

**Acceptance Criteria:**
1. Given 16 active semantic searches held by a controlled dependency, when a 17th arrives, then it receives HTTP 429 and `Retry-After: 1` without invoking the dependency or entering an unbounded queue.
2. Given an embedding request that never completes, when 5 seconds elapse, then its wait is canceled; the API returns a safe dependency-timeout error by 8 seconds and frees its admission slot.
3. Given a disconnected or superseded client search, when cancellation reaches the API, then dependent work receives cancellation and the API releases its concurrency slot within one second without waiting for the full deadline.
4. Given service quotas and concurrency limits, when a load test exceeds them, then rejected requests do not create new embedding work and request-associated memory returns to within 20% of the post-warm-up baseline within 60 seconds after load drains and a full collection in the instrumented test environment.

## L2-034: Persistence and recoverable indexing
**Traces to:** L1-013

Published metadata, revisions, and unfinished indexing work shall survive restarts. SQL Server Express or LocalDB shall hold catalog persistence through Quarry.Infrastructure. Search indexes shall be recoverable from catalog metadata.

**Acceptance Criteria:**
1. Given a saved published revision, when the API and persistence connection restart, then catalog and details return that revision with unchanged IDs and metadata.
2. Given an accepted metadata update interrupted before indexing completes, when the service restarts with healthy dependencies, then it resumes or discovers pending work and restores searchability within 60 seconds of recovery.
3. Given a lost or deliberately cleared vector index in an isolated recovery test, when documented rebuild is invoked for the 1,000-entry benchmark catalog, then all current published entries become searchable within 30 minutes with healthy dependencies, and draft/deleted entries are excluded.
4. Given a database failure during a metadata save, when the operation ends, then it reports failure and does not leave a partially published metadata revision or falsely mark the new revision indexed.

## L2-035: Current-query response ordering
**Traces to:** L1-013

The frontend shall associate every request with its query, technology, and browse-page state and shall render only responses applicable to the current state.

**Acceptance Criteria:**
1. Given search A followed by search B, when B completes before A, then B's results and heading remain visible after A eventually completes.
2. Given an active search, when technology changes and the earlier response arrives later, then it cannot replace results for the current technology.
3. Given browse pagination in flight, when the user submits a query or resets discovery, then the old page response cannot append cards to the new state.
4. Given a failed obsolete request, when a newer request has succeeded, then the obsolete failure cannot show an error over the newer results or clear selection.

---

## L2-036: Loading, unavailable, and incomplete-result states
**Traces to:** L1-013

Quarry shall expose distinct states for work in progress, valid empty results, incomplete indexing, and service failure, preserving the user's recoverable input and selection.

**Acceptance Criteria:**
1. Given a submitted request that has not resolved, when the next render occurs, then a loading status identifies the current query or browse operation and previous-query cards are not presented as current results; query and filter controls remain usable.
2. Given API 503, dependency timeout, or network failure, when the request ends, then Quarry displays a service-error state with an explicit retry action and retains draft/submitted query, technology, and selection. Retry submits the current state.
3. Given a search with excluded entries awaiting reindexing, when it succeeds, then any returned recommendations carry a notice that results are temporarily incomplete; zero returned entries produce an indexing notice and retry/browse actions rather than a definitive no-match claim.
4. Given unavailable embedding service but available catalog persistence, when semantic search fails, then `Browse all frameworks` still loads the catalog without requiring the embedding service.
5. Given a transient error followed by successful retry, when the response arrives, then the error/loading state clears and the returned results and count appear without duplicate cards.

---

## L2-037: Health, diagnostics, and operational configuration
**Traces to:** L1-013

Operators shall be able to distinguish process liveness, catalog readiness, search readiness, and indexing health. Diagnostics shall expose correlation, outcome, and timing without raw query content.

**Acceptance Criteria:**
1. Given a live process and unavailable database, when health is checked, then liveness remains healthy and catalog readiness reports unhealthy; given only embedding/index failure, then catalog readiness remains healthy while search readiness reports degraded or unhealthy as appropriate.
2. Given a successful request, a failed request, and an index failure, when diagnostic records are inspected, then each records a correlation or work ID, operation, duration, outcome, and safe error category; index records also identify framework ID and source revision.
3. Given indexing backlog, when operational metrics are inspected, then pending entry count, oldest pending age, failure count, and searchable revision information identify whether the 60-second freshness target is breached.
4. Given invalid required persistence or embedding configuration, when the service starts, then it fails readiness with an actionable operator message and does not claim semantic search is ready; secret values and stack traces are absent from public responses.
5. Given a public health response, when fetched anonymously, then it exposes only coarse status; detailed dependency destinations, configuration, and diagnostics are restricted to operators.

## L2-041: Isolated behavior tests and real integration evidence
**Traces to:** L1-015

Frontend acceptance tests shall use Playwright and Page Objects with shared backend fixtures. Separate API, retrieval, and framework checks shall establish the behaviors that frontend mocks cannot prove.

**Acceptance Criteria:**
1. Given no live API, database, or embedding service, when frontend acceptance tests run, then all backend interactions are intercepted by shared fixtures, unexpected backend requests fail the scenario, and page actions are encapsulated in Page Objects.
2. Given success, empty, delayed, out-of-order, 404, 429, 503, timeout, and incomplete-index fixtures, when the associated scenarios run, then they verify the user-visible outcomes in this specification rather than internal implementation structure.
3. Given persistence, actual semantic retrieval, and independent framework delivery requirements, when release evidence is assembled, then isolated SQL-backed API checks, real-model retrieval evaluation, and built-package consumer checks cover them; passing frontend mocks alone is insufficient.
4. Given a future stated real-time feature using SignalR, when its frontend acceptance tests run, then SignalR interactions are mocked as shared fixtures and no live hub is required. This baseline introduces no real-time feature.

## Acceptance-test trace convention

Every implementation acceptance-test file must start with a comment header identifying its L2 coverage. Each individual test must also identify its covered L2 IDs in a comment or test annotation when the file covers multiple requirements.

```typescript
// Acceptance Test
// Traces to: L2-010, L2-017
// Description: Technology filtering preserves relevance and detail-navigation state.
```

The same comment convention applies to C# API acceptance tests. Each L2 must have acceptance evidence at the verification layer appropriate to its criteria; review and workflow requirements use recorded review/check evidence rather than synthetic architecture tests. Existing mock checks are design evidence and do not satisfy production acceptance criteria simply because their flows look similar.

## Design decisions left to implementation planning

The embedding model/provider and calibrated cosine threshold must be selected and recorded by satisfying L2-005 and L2-006. Vector storage and indexing mechanics, maintenance transport, API route names, and cross-technology preview integration must be chosen within the binding constraints and verified against these behaviors. These are implementation choices; none authorizes reducing the acceptance criteria or substituting the mock simulation for production retrieval.
