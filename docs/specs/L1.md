Status: Scope confirmed by the user's instruction to continue on 2026-09-10. Detailed requirements are recorded in [L2.md](L2.md).

- [Project brief](../prompt.md): primary product scope and delivery constraints.
- [Mock guide](../mocks/README.md), [interface](../mocks/src/main.tsx), and [styles](../mocks/src/styles.css): discovery, details, preview, selection, keyboard, and responsive interaction references.

- [Repository instructions](../../AGENTS.md): application boundaries, technology, framework independence, and implementation workflow.

The brief takes precedence over mock implementation shortcuts. Sample framework names, component counts, hand-authored vectors, and similarity thresholds are illustrative; they do not establish a released catalog or production search algorithm. L2-007 explicitly adopts the three-result limit as a production baseline decision. Production recommendations require semantic embeddings and vector search.

The security, performance, reliability, and observability requirements below apply the requirements-engineer skill's production defaults. The baseline uses public discovery without an account and selection retained during the current page session, matching the mock. Account management, cross-device selection, an administrative UI, application generation, and deployment of selected frameworks are outside this baseline. Catalog maintenance and index refresh remain in scope without prescribing a maintenance interface.

## L1-001: Focused project discovery

Quarry shall make describing the intended application in natural language the primary discovery interaction. It shall provide a prominent project search field, explicit search submission, a few example project queries, and minimal surrounding navigation and secondary controls.

## L1-002: Framework catalog and metadata

Quarry shall maintain and serve a catalog of independently maintained UI component frameworks. Each framework shall have an identity, name, meaningful description, descriptive tags, supported frontend technology, component information, capabilities, and suitable use cases. Catalog information shall describe actual supported capabilities and remain consistent across browsing, recommendations, and details.

## L1-003: Semantic framework recommendations

Quarry shall recommend frameworks by the meaning of the user's application description, including related wording absent from framework names and descriptions. Recommendations shall be ranked by semantic relevance using embeddings of framework descriptions and tags and of the query. Changes to searchable framework metadata shall refresh its indexed representation.

The discovery experience shall support the brief's Animal Hospital and veterinary-clinic examples with frameworks relevant to appointment booking, intake, patient and client record interfaces, and practice operations. Online-store and analytics-dashboard queries shall produce recommendations relevant to their different capabilities.

## L1-004: Catalog browsing, technology filtering, and search recovery

Quarry shall allow catalog browsing with an empty query and provide a secondary filter for supported frontend technology. Filtering recommendations shall preserve relevance order. Insufficient matches and incompatible filters shall produce honest empty states with ways to revise the query, change technology, or reset discovery. Users shall be able to clear search independently and reset both search and filtering.

## L1-005: Understandable and grounded recommendations

Each recommendation shall show the framework name, description, tags, supported frontend technology, and a short explanation grounded in its capabilities and relevance to the project. Quarry shall distinguish component capabilities from complete applications and shall not imply clinical functionality, domain compliance, or unsupported capabilities. It shall not present invented confidence percentages.

## L1-006: Framework details and interactive component previews

Users shall be able to inspect a framework's metadata, capabilities, suitable use cases, and applicable recommendation explanation, and interact with component previews before selecting it. Preview interactions shall remain confined to the preview. Returning from details shall preserve the query, technology filter, result order, and selection, and restore an appropriate keyboard focus location.

## L1-007: Single-framework selection

Users shall be able to select one framework, see and review the current selection while continuing discovery, replace it with another framework, and clear it. Selection shall reflect framework identity and capabilities and shall remain available throughout the current page session and detail navigation.

## L1-008: Themeable frameworks and appearance-independent discovery

Every hosted framework shall support custom themes and skins, including user-chosen colors during implementation. Quarry shall briefly explain this flexibility during discovery and selection. Example styling shall not influence recommendation ranking or framework suitability. Discovery shall exclude palette galleries, swatches, color filters, preset-color comparisons, and color-selection steps.

## L1-009: Independently usable and maintainable frameworks

Each hosted framework shall remain buildable, testable, releasable, and usable independently of Quarry, its backend, and other hosted frameworks. Each framework shall retain its technology choices and provide its component library, companion applications, documentation, examples, tests, and independently buildable design system as needed for that framework's delivery.

## L1-010: Responsive and accessible discovery

All discovery, browsing, filtering, recommendation, detail, preview, selection, and recovery flows shall remain usable across extra-small, small, medium, large, and extra-large viewports. Users shall be able to complete these flows with a keyboard and assistive technology, with meaningful labels, visible focus, understandable status changes, readable content, and controls that remain reachable without obstructing essential content.

## L1-011: Secure discovery and protected data

Quarry shall support public discovery and local selection without requiring an account. It shall validate untrusted inputs, safely display queries and catalog content, protect transport and secrets, and prevent unauthorized catalog or index changes. Any exposed maintenance operations shall require authentication and authorization. Query processing, component previews, diagnostics, and embedding integrations shall protect user-entered information and resist injection and resource abuse.

## L1-012: Responsive performance and bounded resource use

Quarry shall provide predictable response times for browsing, semantic recommendations, filtering, details, and selection under a defined catalog size and concurrent workload. Search, indexing, and preview operations shall use bounded resources. L2 shall define measurable latency, workload, timeout, and resource limits that can be verified before release.

## L1-013: Reliable operation and diagnosable failures

Quarry shall preserve catalog data across service restarts and keep search results consistent with the indexed catalog. It shall distinguish loading, valid empty results, and service failures; preserve recoverable discovery state; and provide actionable recovery when catalog, embedding, indexing, or preview operations fail. Operators shall be able to determine service health, request failures and latency, and index freshness without exposing sensitive query content or internal errors to users.

## L1-014: Standalone and honestly labeled design mock

Quarry shall retain a standalone interactive design artifact demonstrating the discovery, recommendation, filtering, detail, component-preview, and selection flows using a local illustrative catalog without a live backend. The artifact shall clearly label its sample data and simulated recommendations. Its verification shall include Animal Hospital, related veterinary wording, online-store and analytics-dashboard examples, empty queries, unmatched queries, technology filtering, and desktop and mobile interaction. Simulation shall not be accepted as implementation of production semantic search.

## L1-015: Maintainable delivery and behavioral verification

Quarry shall support focused, independently reversible implementation increments, with acceptance tests traced to detailed requirements and observed failing before implementation. Relevant tests and builds shall pass before each implementation increment is committed. Frontend acceptance tests shall run without a live API or database, and verification shall assess behavior rather than physical repository layout. Shared application concerns and independently released frameworks shall remain clearly separated, using the smallest solution that meets current requirements.

## Binding implementation constraints

These constraints come from the brief and repository instructions; they accompany the capability requirements and must be carried into L2 or referenced implementation review criteria without creating tests for physical file placement.

- Quarry application code belongs in `frontend/` and `backend/`; publishable frameworks belong in `frameworks/`.
- The Quarry frontend uses React and TypeScript `.tsx` components, with `frontend/` as the npm workspace root and `frontend/apps/quarry/` as the application location.
- The backend uses .NET, ASP.NET Core controllers, SOLID principles, and Microsoft.Extensions for dependency injection, options, configuration, and logging.
- Clean Architecture uses `Quarry.Domain`, `Quarry.Application`, `Quarry.Infrastructure`, and `Quarry.Api`, with dependencies directed inward toward Domain and Application.
- Application use cases use MediatR pinned to `12.5.0`; persistence resides in Infrastructure and uses SQL Server Express or LocalDB. The vector-search integration must respect those constraints; its implementation is a design decision.
- Each class, interface, record, struct, enum, or TypeScript type alias in the frontend and backend has its own file.
- Frontend acceptance tests use Playwright, the Page Object Model, and shared backend mocks and data fixtures. All backend interactions, including SignalR if introduced for a stated real-time requirement, are mocked in these tests.
- Framework workspaces separate the library, documentation app, manual development app, deterministic acceptance-test app, marketing site, and design system. Directories are created as their contents are needed, following `AGENTS.md`.
- Generated builds, dependencies, and test reports stay out of source control. Design artifacts retain their ATDD exemption; executable application code and test mocks do not.
